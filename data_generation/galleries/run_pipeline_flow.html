Affogato bimanual affordance data pipeline。本文件 step-by-step 拆解 data_generation/run_pipeline.ipynb（與其匯出版 run_pipeline.py）， 重點標出兩個語言模型 Gemma-3-4B 與 MolmoPoint-8B 各自的 prompt / input / output。

0 · 總覽與資料流

目標：對 gobjaverse 的 3D 物件，產生 role-conditioned bimanual affordance — 也就是「雙手操作某物件時，每隻手該碰哪個 3D 區域」的 heatmap。整條 pipeline 串接四個元件：

① Gemma-3-4B LLM · 上游
看多視角圖 → 判斷可操作性、抽部件、推理雙手分工。產出 output_components.json（含 question / answer 兩個 role）。不在本 notebook 執行，是預先跑好的輸入。
▼ output_components.json（answer = 兩個部件名）
② MolmoPoint-8B LLM · 本 notebook 核心
每個 role × 每個 view 各跑一次 pointing。輸入「圖 + 一句 part-name query」，輸出 2D 點座標（取 top-1）。
▼ 每 (view, role) 一個 2D 點
③ SAM2 分割 · 非 LLM
用 Molmo 的點當 prompt → mask logits → sigmoid → 再乘上以該點為中心的 Gaussian 權重 → 2D probabilistic heatmap。
▼ 每 (view, role) 一張 2D heatmap
④ Multi-view Voting 幾何 · 非 LLM
把 3D 點雲投影到每個 view，做可見性檢查，平均所有可見 view 的 heatmap 分數 → 每個 3D 點、每個 role 的 affordance score。
一句話總結：這個 notebook 真正執行的「語言模型」只有 MolmoPoint-8B 一個。 Gemma 的角色是離線預生成 output_components.json，notebook 只是把它讀進來當文字輸入。SAM2 與 voting 都是非 LLM 的後處理。

3 · LLM #1：Gemma-3-4B（上游語意層）不在本 notebook 執行

Gemma 負責把「3D 物件」轉成「結構化的雙手操作語意」，產物即 output_components.json。 以下 prompt 取自 prototype ../bimanual_annotation/，分三階段（外加一個 yes/no gate）。 註：產生 question/answer 欄位的最終版生成腳本未在 repo 內，但其工作可由輸出 schema 還原。

3.0 Gate：是否適合雙手操作 (is_bimanual.py → output_components 的 operable)

Prompt
System: You are an expert in object affordance and human-object interaction. User: Given an image, determine whether the object is suitable for bimanual (two-handed) manipulation. Answer strictly with one word: yes or no. Do not explain.
Input
單張 RGB（物件某一視角）
Output
"yes" / "no" → 寫成 operable。false 時下游 整筆跳過。

3.1 Step 1 — Per-view 部件抽取 (parse，每個 view 跑一次)

Prompt
System: You are a visual parser. User: The object category is: {object_name}. From this image, list ONLY visible components. Return JSON: { "visible_components": ["...", "..."] } Rules: only clearly visible parts · do NOT guess hidden parts · short consistent names · JSON only
Input
RGB（4 個取樣視角，逐一）+ object_name
Output
每視角一份 visible_components: [...]

3.2 Step 2 — 跨視角合併 (aggregate，純文字)

Prompt
System: You are a semantic reasoning system. User: Object: {object_name}. Below are visible components detected from multiple views: {all_components} Task: merge into a consistent set of meaningful components. - merge synonyms · remove duplicates · remove non-functional parts (logos/text/decoration) - keep parts that are physically/visually distinct & relevant for interaction Return JSON: { "canonical_components": ["...", "..."] }
Input
Step 1 收集到的所有 visible_components（多視角合集，純文字）
Output
canonical_components: [...] → 對應 final_components

3.3 Step 3 — 雙手 affordance 推理 (reason，純文字)

Prompt
System: You are an expert in bimanual manipulation. User: Object: {object_name}. Available components: {components} Task: explain how a human manipulates this object using two hands. Return JSON: { "reason": "...", "affordance_parts": ["...","..."], "left_hand": "...", "right_hand": "..." } Rules: ONLY use listed components · don't invent/refine parts · physically plausible
Input
合併後的 components
Output
reason + affordance_parts（≈ 最終 answer 的兩個部件）。
prototype 還會輸出 left_hand/right_hand，但 output_components.json 已改為 hand-agnostic 的 answer list，與 molmo_prompt_format.md 的規範一致。
Gemma → Molmo 的交接點：affordance.affordance_parts ≈ answer = ["Stand", "Monitor Frame"]。 這個 2 元素 list 就是下游兩個 role（role_move, role_action）的部件名來源。

4 · LLM #2：MolmoPoint-8B（notebook 核心）Step 12

4.1 Role / Query 組裝 (notebook cell 27)

ROLE_QUERIES = {
    "role_move":   f"Point to the part of the {name} that is the {answer[0]}.",
    "role_action": f"Point to the part of the {name} that is the {answer[1]}.",
}

以 Monitor（answer=["Stand","Monitor Frame"]）為例，實際送進 Molmo 的兩句 query：

role_move → "Point to the part of the Monitor that is the Stand." role_action → "Point to the part of the Monitor that is the Monitor Frame."

採用 molmo_prompt_format.md 的 Template B（part-name）：用部件名而非動詞，避免多 role 的 attention 塌到同一個顯著區域。每個 role 一定各跑一次推論（多 role 塞同一句的話，回來的點分不清誰是誰）。

4.2 單張推論：molmo_query_image() (cell 28)

Input
1 張 PIL RGB image + 1 句 query text（messages: image + text）
生成
max_new_tokens=200，greedy，inference_mode + bf16 autocast
Raw out
decode 後的文字，含 Molmo pointing token：<points coords="frame idx x y ..."/>（座標 0–1000 千分比）
解析
extract_image_points(...) 用 processor 回傳的 metadata（token_pooling / subpatch_mapping / image_sizes）把 token 還原成 影像座標 (x,y)
取點
只留 top-1：extracted[0] 的 (x,y)。Molmo 解碼順序即 confidence 順序。0 點 → 回空 list []
extracted = extract_image_points(output_text=generated_text, pooling=..., mappings=...,
                                 image_sizes=metadata["image_sizes"], ...)
if len(extracted) > 0:
    _, _, x, y = extracted[0]      # (frame, idx, x, y) → 取 x,y
    pts = [np.array([x, y])]
else:
    pts = []                       # 該 (view,role) 無點 → 之後 heatmap 全 0

4.3 全掃描：per-role × per-view

迴圈
2 roles × 24 views = 48 次 Molmo 呼叫
輸出結構
molmo_points_per_view_per_role[role][view_idx] = [np.array([x,y])] 或 []

每個 view 存一張標星號的圖到 output/{id}/molmo/molmo_view_{i}.png
fallback 未實作：molmo_prompt_format.md 設計了 A→B→C 三段 fallback（primary 回 0 點時改用 part-name → functional-region）。 目前 notebook 只跑 Template B 一次；回 0 點就直接記為 missing（heatmap 全 0、該 view 不參與該 role 投票）。

6 · SAM2 + 3D voting 的數學重點

SAM2 heatmap

heatmap = sigmoid(best_mask_logits) × gaussian_weight(center=molmo_point, σ=77)。 Gaussian 把信心集中在 Molmo 點附近，避免 SAM2 把整個大區塊都算進去；多點時取各 Gaussian 的 max（union）。

Voting（2D heatmap → 3D 分數）

cam = w2c · P_world                       # 世界 → 相機
uv  = (K · cam_xyz) / z                    # 投影到像素
visible = in_front & in_bounds & (z < sampled_depth·(1+tol))   # 遮擋檢查
score[p] = mean over visible views of heatmap[v,u]            # 平均

每個 3D 點的最終 affordance = 它在「能看到它」的所有 view 上的 heatmap 值的平均。被遮擋/看不到的 view 不貢獻。

8 · 觀察與注意事項

  • notebook 只跑 Molmo。Gemma 是離線預生成 output_components.json；要理解 Gemma 行為需看 ../bimanual_annotation/。
  • question 欄位未被使用。Molmo query 直接用 answer[0]/answer[1] 兩個部件名（Template B），question 只是被讀進來 print。若想用自然語句 query，需改 ROLE_QUERIES。
  • role 數寫死為 2（role_move=answer[0]、role_action=answer[1]）。3+ roles 或 answer 不足 2 個會出問題。
  • Molmo fallback 未實作（spec 有 A→B→C，notebook 只跑一次）。建議追蹤每筆的「0 點 view 比例」。
  • notebook vs .py：notebook 是單物件互動版（DATA_INDEX，預設 49）；run_pipeline.py 是批次版（--start/--end/--gpu，含 operable gate、自動存 png/html），兩者核心流程一致。
  • 座標系：讀相機時 Y/Z 取負，投影前再 flip_yz；depth near plane = √3/2（物件被 normalize 進單位球）。改資料來源時要重新確認。
  • 路徑相對性：讀 output_components.json / dataset/... 用相對路徑，需從 data_generation/ 執行。
